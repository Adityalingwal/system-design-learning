Lesson 0001 · P0 Design Process · Section 12 · Deep

Boxes banane se pehle kya karte hain

Har design ka ek standard raasta: requirements → estimation → entities → API → boxes → deep dives.

Problem: boxes pehle, sawaal baad mein

Maan lo assignment mila: "Ek voice agent platform design karo." Pehla instinct hota hai seedha diagram kholna: LiveKit, STT, LLM, TTS, Redis, Postgres, Kafka... 20 minute mein 12 boxes ban gaye. Phir koi poochhta hai: "Ye kitne callers handle karega? Reply kitni der mein aana chahiye? Call ka data kitne din rakhna hai?" Aur tab samajh aata hai ki tumne ek unknown problem ka solution bana diya.

Wajah simple hai: boxes requirements se aate hain. Ek voice agent jo din mein 5 calls leta hai aur ek jo 5,000 calls ek saath leta hai — dono ka design bilkul alag hoga. Bina poochhe tum pehla bana rahe ho ya doosra, pata hi nahi.

Idea: ek fixed raasta

Design ko ek line mein todte hain. Har step ka ek output hai, aur har output agle step ka input banta hai.

 1. Requirements        "Kya banana hai? Kitna achha chahiye?"
        |
 2. Estimation          "Kitna bada? Ek machine kaafi ya kai?"   (sirf jab design badle)
        |
 3. Core entities       "Kin cheezon ki baat ho rahi hai?"       User, Call, Appointment
        |
 4. API                 "Bahar se system se kya maanga jaata hai?"

Step 1 gehra: requirements

Ye sabse zaroori step hai, kyunki baaki sab ispe tika hai. Isse do hisson mein todte hain.

Functional: "system kya kare"

"User ye kar sake" jaise statements. Source ke hisaab se top 3 chuno. Lambi list tumhe nuksaan karti hai, kyunki saare features ka design karna possible hi nahi. Prioritize karna khud ek skill hai.

Non-functional: "system kitna achha ho"

Ye system ki quality hai: speed, availability, data safety. Do rules:

  1. Number lagao. "Low latency" kuch nahi bolta, har system ko low latency chahiye. "Search results 500 ms ke andar" ek target hai, aur batata hai ki system ka kaunsa hissa sabse zyada matter karta hai.
  2. Top 3-5 hi chuno. Neeche ki checklist se wo chuno jo is system ke liye sabse zyada matter karti hain.

Worked example: tumhari duniya se

Problem: "Ek clinic ke liye voice agent, jo phone pe appointment book kare."

Functional (top 3)

  • Caller appointment book kar sake
  • Caller appointment reschedule ya cancel kar sake
  • Agent na samjhe to call human ko transfer ho jaaye

Non-functional (example numbers, maine assume kiye hain, fact nahi)

  • Latency: caller bolna band kare, uske ~1 second ke andar agent ka jawab sunai dena shuru ho
  • Scalability: 200 calls ek saath, subah 9-11 baje peak
  • Durability: confirm ho chuka appointment kabhi lost nahi hona chahiye
  • Compliance: call recording aur patient ka data sensitive hai, consent chahiye

Dekho kya hua: "200 concurrent calls" ne tay kar diya ki ek server se kaam nahi chalega. "Appointment kabhi lost nahi" ne tay kar diya ki booking ek durable database mein jaayegi, sirf memory mein nahi. Boxes ab apne aap sawaal ban gaye.

Estimation: kab, kaise (preview)

Estimation ka matlab hai thoda hisaab lagana: kitni requests/second, kitna storage. Source ka rule: sirf tab karo jab result design badle. "Bahut saari traffic hai, ok" nikalne ka koi faayda nahi. Agar answer ye decide karta hai ki ek machine kaafi hai ya kai chahiye, tab karo. Ye hamari NOTES ke "math tabhi karo jab design badle" se match karta hai. Kaise karte hain, wo agla lesson hai (numbers to know ke saath).

Trade-offs

Pehle simple design, phir complexity (deep dives mein). Plus: ek poora chalne wala design jaldi mil jaata hai, aur complexity wahin judti hai jahan requirement maangti hai. Minus: pehla diagram "adhoora" lagta hai. Source ki salah: cache ya queue jaisi jagah dikhe to ek chhota note likho aur aage badho.

Kam requirements vs zyada requirements. Kam: focus rehta hai, design poora hota hai. Zyada: lagta hai "complete soch rahe ho", par kuch bhi gehraai se nahi ho paata. Hum kam chunte hain aur baaki ko khud bolke "out of scope" kehte hain.

Aam galtiyan

1. Vague requirement. "System fast aur scalable hona chahiye" — kisi kaam ka nahi. Number lagao, aur batao kaunsa hissa.

2. Seedha boxes. Requirements ke bina component list banana. Har box ke peeche ek requirement hona chahiye; na ho to wo box hataao.

3. Pehle hi complexity. Kafka, sharding, multi-region, sab pehle diagram mein daal dena. Isse design kabhi poora nahi hota.

4. API mein user ID body se lena. Current user hamesha auth token se aata hai, request body se nahi, warna koi bhi dusre ke naam se kaam kar sakta hai. (Source ki API wali baat.)

Yaad rakhne wali baatein

"Text chhupao" dabao, phir apne shabdon mein bolo (chat mein, Hinglish chalega). Check karne ke liye dikhao.

Order
Requirements → estimation (agar design badle) → core entities → API → high-level design → deep dives.

Functional
Top 3 "user ye kar sake". Lambi list nahi.

Non-functional
Top 3-5, number ke saath, aur is system ke hisaab se chune hue.

Rule
Har box kisi requirement ki wajah se hai. Complexity deep dives mein aati hai.
